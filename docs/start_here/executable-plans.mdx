# Plan hygiene — extract, then remove

> **This is not a plan format.** Developers, users, and agents may plan however they like: Superpowers, Cursor plans, engineering-loop, GitHub Issues, `TODO.md`, ad-hoc markdown, or no file at all. Skill Steward does **not** define or require a new planning template.

This page explains **why** plan artifacts should not stay in the repo as source of truth after work finishes — and **where** durable knowledge should go instead.

The same instinct applies to overgrown non-plan docs: keep the canonical owner, merge or delete duplicate surfaces, and move deterministic repeated truth into checks instead of prose. For broader plans/specs/docs/skills/tools/evidence cleanup, run a Repository Ecology Review through `repo-quality-system-lifecycle`; plan hygiene is one ecology case, not the umbrella.

## The rule (format-agnostic)

When work is **done**:

1. **Extract** everything still true into durable homes (table below).
2. **Remove** the plan artifact from the repo (or move it to an explicit archive that agents are told **not** to execute).

Plans are **scratch paper**, not documentation. Keeping finished checklists in-tree misleads the next agent (same failure mode as a bloated `AGENTS.md`).

## Where extracted knowledge goes

| Outcome type | Land in |
|--------------|---------|
| Strategic choice, trade-off | [ADR](../decisions/README) |
| Standing why / how | [DESIGN_FAQ](../DESIGN_FAQ) / [DX_FAQ](../DX_FAQ) |
| Behavior, gates, automation | Code, CI, CLI, MCP, `plugins/` |
| Repeatable agent procedure | `skills/{name}/SKILL.md` |
| Charter / scope change | [North Star](../NORTH_STAR) + ADR if significant |

## Doc retirement dispositions

When a cleanup finds stale or overlapping docs, choose one explicit disposition:

| Disposition | Use when |
|-------------|----------|
| Keep | This is the canonical owner and still current. |
| Merge | Another live guide should absorb the remaining truth. |
| Move to ADR | The durable value is a decision or trade-off. |
| Move to FAQ | The durable value is standing why/how guidance. |
| Move to skill | The durable value is repeatable agent procedure. |
| Move to check | The durable value is deterministic failure, drift, or generated freshness. |
| Move to consumer proof | The producer owns architecture; this repo only needs adoption evidence or local deltas. |
| Delete | The content is implemented, stale, duplicated, or no longer useful after extraction. |

## Any planning tool is fine

| You might use… | Guild stance |
|----------------|--------------|
| [Superpowers](https://github.com/obra/superpowers) / spec-driven programs | OK — use `docs/superpowers/` (or equivalent) in **your** repo; see `repository-governance-lifecycle` skill |
| Cursor / Codex session plans | OK — ephemeral by default |
| `docs/exec-plans/active/` in this repo | **Optional** scratch only; not a standard |
| Issues / Projects | OK — tracking outside git truth |

**Do not** treat this repo’s `docs/exec-plans/` as “the Guild plan format.” It exists only as optional short-lived storage for maintainers who want a file in-tree during a PR.

## Optional in-repo scratch (`docs/exec-plans/`)

`docs/exec-plans/active/` is the conventional scratch location for in-flight plan files. It has no README — this page is the doctrine. Rules:

1. Name files `YYYY-MM-DD-short-title.md` (or your own path).
2. Link the file from the PR.
3. On merge: extract durable knowledge → **delete** the file (or write a one-line summary in ADR Notes).

## Anti-patterns

- Finished checklists left in `ROADMAP.md`, `docs/plans/`, or `TODO.md` as if still current
- Duplicate plan + ADR with the same “truth”
- Archived phase plans executed as if they were the live tracker (use tracker/spec + closure in Superpowers-style layouts, or delete/archive)
- Consumer docs that copy producer architecture instead of linking to the owner and recording local proof
- Repeated operational prose that should be a validator, generator freshness check, test, or harness probe

## Agent workflow

1. Read [North Star](../NORTH_STAR) before multi-step work.
2. Plan with **whatever** the user or product repo already uses.
3. On completion: extract → ADR / FAQ / code / skill → **remove** the plan file.
4. For doc cleanup, name the retirement disposition before deleting or merging.
5. Update [docs_map](docs_map) only if navigation changed.
