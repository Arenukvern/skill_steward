# Work discipline

This is the only standing procedure for ordinary repo work. Skills point here. They do not restate it.

1. Name the use-path that must become true.
2. Two attempts on the same owner with no new evidence, then rewrite, delete, or hand off. Do not open a third local patch.
3. One obligation per claimant. Adjacent finds go in the handoff. Do not absorb them.
4. Prove the product use-path before adding fixtures.
5. Run the native gate you will rerun. A suite too slow to run on the edit is the bug.
6. Keep the plan a spine. Fold into the open item, or extract and delete. Do not open a parallel queue.

Before editing a shipping repo (`app`, `library`, `cli_tool`, `plugin`, `harness`), name the product use-path. If the only diff would be `steward.yaml`, a fixture, an eval case, or an evidence note, stop or leave the work native.

`steward map`, `steward adopt` (once), and `steward claim check` (only when a readiness sentence is about to be said) are the Steward front door. The delivery gate is `quality.validate` in `steward.yaml`. `steward doctor` and the other commands are maintainer health tools. Do not start there.

A handoff or a parallel batch does not create an owner. Skill Steward does not schedule claims or presence. Do not add more baton fields to pretend that it does.

`moe_required_for_architecture` defaults off for shipping archetypes. Mixture of Experts is optional critique for ADR-level `amends` or `conflicts`, not a preflight.
