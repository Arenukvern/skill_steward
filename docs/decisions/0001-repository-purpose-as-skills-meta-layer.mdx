# Skill Steward as Engineering Stewardship for agent-operated repositories

## Context and Problem Statement

The open Agent Skills ecosystem (`npx skills`, [skills.sh](https://skills.sh), [agentskills.io](https://agentskills.io/)) makes it easy to publish and install instruction packages. At the same time, agent-operated engineering repositories now need more than packages: they need charter clarity, docs maps, ADRs, validation commands, safe action contracts, release evidence, and feedback loops that let humans and agents work on the same software ecology.

Skill Steward was bootstrapped with marketplace scaffolding and starter skills. Without an explicit charter, it risks being read either as “another bag of skills” or as a product runtime. Neither is right.

**Why should this repository exist, and what belongs here?**

## Decision Drivers

* **Repository stewardship**: Optimize for whole-repo legibility and quality, not only agent internals or feature delivery.
* **Meta, not domain runtime**: Prefer capabilities that help teams govern, compose, review, validate, and improve repos and agent workflows; do not replace product/domain code or specialized skill libraries.
* **Cross-repo**: Work for apps, libraries, tools, plugins, harnesses, and meta repos.
* **Cross-agent**: Installable via `npx skills` into Cursor, Claude Code, Codex, Zed, and peers without forked formats.
* **Continuous improvement**: Support evolving processes (handoffs, ADRs, validation, retros, evals, action contracts) rather than one-off prompts.
* **Plugins as well as skills**: Room for installable plugins, hooks, automations, and registry glue where a skill alone is insufficient.
* **Sustainable maintenance**: A small structural surface a maintainer can keep correct beats a wide domain catalog that rots.

## Considered Options

* **A. General-purpose skills marketplace** — Accept any contributed skill; optimize for breadth and skills.sh leaderboard presence.
* **B. Curated domain guild** — Deep skills for one stack only (e.g. Flutter, Firebase, MCP).
* **C. Engineering stewardship layer** — Narrow artifacts, broad applicability: skills, plugins, docs, specs, validation patterns, and quality contracts for agent-operated repos.
* **D. Documentation-only org** — No installable packages; ADRs and guides only.

## Decision Outcome

Chosen option: **C. Engineering stewardship layer**, because it gives Skill Steward a clear reason to exist alongside larger marketplaces and product harnesses. Agent Skills are a delivery surface; the object of stewardship is the repository as a whole.

### Consequences

* Good, because contributors can reject out-of-scope PRs with a documented charter.
* Good, because apps, libraries, tools, plugins, harnesses, and meta repos can share a structural quality vocabulary without sharing domain code.
* Good, because `repo-quality-system-lifecycle`, `repository-governance-lifecycle`, `steward validate`, `skill-eval-improve`, and `multi-agent-handoff` are exemplars of the intended shape.
* Bad, because the repo will not replace specialized skill libraries or product harnesses; users must install or build domain capabilities elsewhere.
* Bad, because broad applicability requires careful language so stewardship does not become an everything bucket.
* Neutral, because skills.sh listing remains useful for discovery, but popularity is not the primary success metric.

### Confirmation

* New skills are evaluated against the inclusion criteria below before merge.
* README and docs lead with Engineering Stewardship for agent-operated repositories.
* `docs/repo-quality-contracts.mdx` defines repo-level quality contracts separately from the Agent Skills package spec.
* Follow-up delivered in [ADR 0004](0004-plugin-packaging-and-install-path) (`plugins/` layout and install paths).

## Inclusion criteria (what belongs in Skill Steward)

| Include | Exclude |
|---------|---------|
| Repository governance, quality contracts, docs lattice, ADR/FAQ loops | Framework-specific coding guides (React, Flutter, cloud recipes, etc.) |
| Authoring, validating, and publishing Agent Skills | Large reference corpora copied into skills |
| Reviewing skill quality and spec compliance | One-off prompts with no reuse story |
| Registry/marketplace hygiene (index, validate, list) | Skills that duplicate official vendor packs without meta value |
| Small plugins that enforce or automate stewardship workflows | Heavy applications or long-running product services in-repo |
| Continuous improvement loops (retro, update, deprecate, eval, handoff) | “Everything bucket” contributions |
| Harness/action-contract culture and proof patterns | Product-specific runtime harness ownership |

**Size rule of thumb:** prefer one clear outcome per skill; keep `SKILL.md` lean; push depth to `references/`; use scripts only when they save context or enforce checks.

## Repository shape (intended)

```text
skill_steward/
├── skills/           # Installable stewardship skills (small, focused)
├── plugins/          # Hooks/automation packages and wiring descriptors
├── docs/             # North Star, specs, concepts, decisions, FAQ lattice
├── packages/         # Steward CLI source and tests
├── scripts/          # Repo-level validation and tooling
└── templates/        # Scaffolding, not published as skills
```

Domain knowledge stays in the governed product/domain repositories. Skill Steward links to those practices by pattern, not by ingesting their content.

## Pros and Cons of the Options

### A. General-purpose marketplace

* Good, because fastest growth and skills.sh visibility.
* Bad, because indistinguishable from existing catalogs; high maintenance; violates concise/focused goal.

### B. Curated domain guild

* Good, because deep expertise in one stack.
* Bad, because overlaps vendor and community repos; wrong scope for structural stewardship.

### C. Engineering stewardship layer

* Good, because unique charter; composes with any domain skill set or product harness.
* Good, because aligns with continuous improvement and repo-level quality.
* Bad, because requires discipline to reject scope creep.
* Neutral, because audience is smaller than mass-market skill packs.

### D. Documentation-only

* Good, because zero install surface.
* Bad, because fails the goal of portable procedures, specs, and repo-local tooling.

## More Information

* Y-Statement: In the context of agent-operated engineering repositories, facing hidden local context, stale docs, fragmented skill packages, and unproven quality claims, we decided for an **Engineering Stewardship repository** to achieve **shared structural governance and quality contracts**, accepting that **domain/runtime capabilities must live in their own repos**.
