# Adopt concept doc store (vectorless documentation lattice)

## Context and Problem Statement

Skill Steward documents process and meta-skills (ADRs, FAQ-driven docs, skill validation). Documentation can bloat when it **re-explains code** or relies on **embedding/RAG** instead of explicit structure.

A working pattern exists in sibling product harnesses: layered docs (`docs_map` router, `NORTH_STAR`, ADRs, agent playbooks, optional `superpowers/` programs) where **behavior** stays in code/examples and **docs** hold decisions, concepts, and navigation.

Maintainer practice also uses [FAQ-driven development](https://dev.to/arenukvern/faq-driven-development-or-new-old-way-to-write-docs-rules-prompts-25jl) for compressed Q&A at package level ([ADR 0002](0002-adopt-faq-driven-documentation)).

How should Skill Steward teach agents to organize documentation in other repositories?

## Decision Drivers

* **Vectorless store** — git-native Markdown, routers, and links; no requirement for vector DB as doc system.
* **No duplicate “how code works”** — examples, tests, and source are SSOT for behavior; docs link inward.
* **Human + agent clarity** — separate charter, decisions, concepts, and agent ops.
* **Composable with FAQs** — lattice for repo navigation; DESIGN_FAQ/DX_FAQ for package compression.
* **Reference implementation** — product harnesses analyzed and encoded in `repository-governance-lifecycle`.

## Considered Options

* **Single README** — All knowledge in one file.
* **Wiki / Notion** — External, decoupled from PR review.
* **RAG / embeddings over docs** — Semantic search as primary navigation.
* **FAQ pair only** — DESIGN_FAQ + DX_FAQ without repo-level lattice.
* **Layered concept doc store + optional FAQs** — layered doc lattice + ADR 0002 FAQs.

## Decision Outcome

Chosen option: **"Layered concept doc store + optional FAQs"**, shipped through `repository-governance-lifecycle` with reference analysis of product harnesses.

### Consequences

* Good, because agents get a router and clear SSOT rules before writing prose.
* Good, because ADRs and concepts stay short; code drift reduced.
* Good, because aligns with Skill Steward meta-layer mission (process improvement, not domain tutorials).
* Bad, because more folders than a minimal repo strictly needs.
* Bad, because `superpowers/` program layout is optional but easy to over-adopt.
* Neutral, because public docs sites (docs.page) remain optional publish layer on top of git files.

### Confirmation

* Skill `skills/repository-governance-lifecycle/` with lattice, SSOT, ADR, FAQ, and bootstrap references.
* Cross-link from harness and skill-authoring skills.
* Product harnesses cited as reference implementations in skill and this ADR.

## Layer summary (normative)

| Layer | Holds | Does not hold |
|-------|--------|----------------|
| Router | Links | Technical detail |
| Charter | Why product exists, scope | API lists |
| ADRs | Why codebase shape | Implementation walkthrough |
| Concepts | Architecture mental model | Copy-pasted schemas |
| Agent ops | Install, gates, troubleshooting | Domain recipes |
| Skills | Procedures | Architecture essays |
| Code / examples | Behavior SSOT | — |

## Pros and Cons of the Options

### Single README

* Good, because simple.
* Bad, because becomes unmaintainable; poor agent retrieval.

### RAG-primary

* Good, because fuzzy search on large corpora.
* Bad, because stale chunks; hides structure; not reviewable in PRs as first-class.

### FAQ pair only

* Good, because excellent package-level compression.
* Bad, because missing repo-level router and program discipline.

### Layered concept doc store

* Good, because matches product harness production patterns and user intent.
* Good, because vectorless and link-driven.
* Bad, because initial setup cost for small repos.
