## Lessons Learned

1. **Snapshot usefulness depends on freshness semantics.** The first loops showed that persisted summaries can diverge from console-only benchmark runs. The tool must label saved summaries as persisted history instead of letting `latest` imply current proof.
2. **Docs are not enough for deterministic drift.** The docs route was useful, but the repeated friction belongs in CLI output and tests so future agents see the warning at the moment they inspect the repo.
3. **Readable evidence is not fully replayable evidence.** Future PDSA artifacts should include compact JSON excerpts, output paths, or digests for snapshot, schema, and benchmark payloads when those outputs support the conclusion.
4. **Disposition review should avoid comfortable `keep`.** Templates and evidence/guidance hybrids may deserve `defer with owner` when they are intentionally tolerated but not yet in their ideal home.
5. **Maintainer-local invocations must be labeled.** Raw `dart --packages=... bin/steward.dart` commands are acceptable for dogfood, but they are not adopter instructions.
6. **Usefulness needs friction measures.** Future loops should count docs consulted, commands attempted, missing fields, and whether the next action was discoverable from snapshot alone.
7. **Config validity comes before steward mythology.** `ecsly` is a good candidate for product/engine stewardship later, but current evidence says root Steward config repair or unknown-case capture comes first.
8. **Blocked explanation needs current payloads.** `blocked explain` against an older persisted summary returned an unknown-block route, while the current console benchmark showed `invalid_config`; this later became the `steward blocked explain --stdin --json` hot path.
9. **The current ledger is useful, but not machine-composed.** A future status command should join ledger claim, snapshot inventory, schema drift, claim gate, and blocked routes without awarding maturity. This later became the narrow `steward dogfood status --json` hot-path candidate.
