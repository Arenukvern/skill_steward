## Capability-level adoption definition

Use [mcp_flutter capability-level proof](mcp-flutter-capability-level-proof-2026-06-10) as the acceptance checklist for the first adoption. The claim means every relevant S/H ladder stage is proven for one named capability, not that every workflow in the target repo is mature.

Required artifacts:

- H2 proof loop: `doctor -> actions list -> action inspect -> probe -> benchmark`.
- H4 fresh-agent proof: bounded workflow completed without hidden local context.
- H5 promoted capability: owner, risk/safety, redaction, validation, falsifier, positive proof, and non-claims.
- Generative usefulness: evidence teaches a later agent how to solve or improve a real tool surface while preserving the original user goal.

## Known limits

- Raw machine summaries under `.steward/benchmark-summaries/` are local evidence. Public review uses redacted summaries tracked in `mcp_flutter/docs/evidence/generated/`.
- Scenario `source.commit` is a subject commit. Because updating a scenario creates a later commit, local HEAD can differ from `source.commit`; this is not remote-equivalence proof.
- `mcp_flutter` still reports existing skill metadata/source warnings during `make check-contracts`; they are warnings, not gate failures.
- Broad H5 remains unclaimed until repeated evidence promotes reusable capabilities across producer and consumer contexts with owner, risk, redaction, validation, falsifiers, and fresh-agent proof.
