# Session application review

Skill Steward is useful when it shortens the route to an owner, a safe change,
and a trustworthy native check. Its evolutionary simplicity and evidence
boundaries fit that purpose. The main risk is delivery and procedure overhead:
the session can receive overlapping copies, load more governance than the task
needs, or mistake a static check for observed improvement.

This review applies the existing charter (`north_star_impact: clarifies`); it
does not introduce a new lifecycle, maturity ladder, telemetry service, or skill.

## Dispositions, in priority order

| Bottleneck | Decision and why | Owner / status |
|------------|------------------|----------------|
| Hidden validator failure and duplicate execution | Preserve stderr and terminal status; fallback only when a runner is unavailable. Accept repo-relative paths. This removes work and restores truthful feedback. | Cursor hook: implemented, isolated regression passed. |
| Full workflow before a routine repair | Put a depth decision before the repo-quality workflow: clear owner + native gate goes directly to repair; recurring friction opens only the owning section. | Existing repo-quality skill: candidate guidance implemented. |
| Multiple installed skill copies | Diagnose the advertised path and content hash, choose the intended distribution per scope, and verify discovery in a fresh session after updating through its installer. | DX FAQ: clarified. Global installation changes deferred to their owning install/update flow. |
| Static checks mistaken for behavioral proof | Stop requiring a YAML mirror for every prompt. Keep static regressions for distinct rules; freeze behavioral holdouts before edits and retire exposed cases from unseen acceptance. | Existing eval skill: clarified; existing static oracle unchanged. |
| Old status presented as current effectiveness | The current dogfood ledger explicitly says last verified June 13. Preserve its dated proof; do not treat it as an October session-quality measurement. | Ledger owner: rerun a relevant workflow before upgrading claims; June results not relabeled as newly verified. |
| Heavy skill bodies and overlapping routing | Prefer selective loading and deletion/compression within the owner. Do not split every concern into another skill. Refactor references only after traces show which parts agents repeatedly read unnecessarily. | Follow-up conditional on real session reading/repair cost. |
| Repeated setup and whole-repo checks | Preserve required final gates; reuse dependencies and focused native checks during iteration. Do not add a new validation scheduler from this sample. | Native tooling; hook duplicate execution fixed first. |

## Prediction and observation

Prediction before the hook edit: selecting one available validator would remove
the duplicate attempt while preserving its failure and diagnostics. The fixture
failed before the edit (`expected 7, got 0`) and passed afterward for absolute
and relative paths. Non-skill edits remained ignored. The manifest hash was
updated after validation correctly reported the changed wiring artifact.

The skill changes are plausible reductions in instruction overhead, not a
measured speedup. Existing static evals remain the same oracle. No controlled fresh-agent task-execution comparison was run; the follow-up
guided reasoning check below is weaker evidence. Published H* prompts are
development cases.

## Smallest next behavioral proof

Use ordinary tasks: a small product repair, an ownership/docs repair, and a
repeated validation failure. Freeze acceptance before editing instructions;
compare equivalent clean starting states with native guidance versus one
explicitly selected Steward skill. Record loaded path/ref, task result, time
to first useful action, setup/repair attempts, total elapsed time, and rework.
Keep the model, permissions, available tools, and validation gate comparable.

Start with Codex and Zcode; replay the Cursor hook separately before claiming
host integration. Expand to other clients only after the first comparison is
useful. A win requires equal correctness and lower time or rework on a fresh
repeat. If the entry guidance adds ceremony or suppresses needed ownership
checks, revise or remove it. Store the result in the existing adoption record,
not a new measurement platform.

## Validation

- Hook regression: reproduced failure before repair; passed after repair.
- `pnpm run eval`: 61/61 existing static cases passed; not behavioral proof.
- `pnpm run validate`: passed after refreshing the hook manifest hash (15 skills, including the pre-existing docs-refresh candidate).
- `git diff --check`: passed before final review.
- GitNexus query/impact: mounted server has no `skill_steward` index. No graph-derived blast radius or code-symbol refactor claimed.

The recommendation is to keep the stewardship purpose and compress its entry
cost. Create stronger automation only when repeated session evidence shows
the native path or existing guidance cannot remove the bottleneck.

### Guided reasoning check

Two fresh internal subagents received the same three hypothetical questions:
a routine parser repair, a faster candidate with a correctness regression,
and a protocol-conformant tool whose write had not been observed. Baseline was
instructed not to load skills; treatment read the updated eval skill and its
two references. Both recommended native repair, rejected the quality regression,
and required effect/safety/usefulness evidence beyond protocol conformance.

The treatment gave more measurement detail. No quality uplift is established:
this was a single guided response per arm, no executed product task, no enforced
filesystem isolation, no independently frozen scoring rubric, and no reliable
per-arm token/time measurement. It is a sanity check, not an unseen holdout,
natural-discovery test, Codex-vs-Zcode comparison, or promotion gate. Its cases
are now development examples.

### Follow-up verification and boundaries

- 10 comparator controls passed; combined with existing path, MCP, schema-payload
  and benchmark tests, 39 focused tests passed.
- Comparator and its test file: Dart analysis passed.
- Existing 61 static eval cases passed; acceptance rules were not weakened.
- Skill validation passed for all 15 skills; docs check passed.
- The copied skill's helper runs without repository packages or a network call.
- External benchmark runners/suites were researched, not installed or executed.
- Zcode, Claude Code and Zed behavioral execution remain unmeasured. The official
  MCP conformance route must first match Steward's declared version/transport.

Keep ordinary CI deterministic. Pilot one external runner only when a concrete
agent task suite and isolated client are ready; use local native acceptance as
the outcome oracle. Prefer skillgrade for that bounded pilot, or reuse an
adopter's existing runner. SkillEvaluator/Harbor remain options when repeated
multi-client execution warrants the additional setup. No automatic optimizer,
new maturity tier, or global skill-cache rewrite was added.
