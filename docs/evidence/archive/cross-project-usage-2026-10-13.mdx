## Corrected conclusion

Skill Steward is already adopted and used in ongoing engineering work. The
October two-task pilot cannot answer whether that existing stewardship practice
has production value across the portfolio. Conversely, adoption and useful
artifacts do not by themselves prove that the skills caused faster or better
work than native practice would have produced.

The strongest current positioning is **used across a maintainer's public and
private projects for repository governance, native-check routing, documentation
maintenance and evidence discipline, with auditable examples**. Do not describe
this as merely a proposed adoption experiment, or as independent customer scale.

## What did not work, or remains unproven

1. **Status maintenance lagged actual work.** Steward's central ledger is dated
   June 13 while adopter receipts and sessions continue into September/October.
   Oka retains a September 6 passing smoke receipt; the package collection retains
   an August 20 blocked receipt; another public library retains a June blocked
   receipt. These dates cannot establish today's pass/fail. A stale card made
   actual usage look absent. Refresh the relevant existing row from a new native
   run when its claim matters; do not rewrite historical receipts as current.
2. **Shell success can conceal action failure.** One ZCode command completed
   while the printed action exit was 127, followed by “whitespace clean.” Other
   samples show missing CLI PATH entries, and a quick probe reporting failed
   while piped through `tail`. Preserve the command's exit with `pipefail` or
   capture it explicitly; inspect structured action status, not just tool status.
3. **Eval coverage can be vacuous.** The Oka documentation-skill extraction ran
   an eval that reported `0/0 cases passed` because the new skill was outside
   the T1 list. Later YAML parsing and 205 repository tests are different checks;
   neither turns skipped skill cases into behavioral coverage. Report skip/zero
   coverage directly; do not expand T1 merely to manufacture a green badge.
4. **Setup work consumed effort.** That same session hit missing docs dependencies,
   missing YAML tooling and an incorrect temporary Dart package context before
   reaching native checks. Existing portable commands should be the first route;
   another validator stack adds maintenance cost.
5. **More guidance is not automatically better.** Installed-copy drift and the
   repaired validation-hook failure remain documented in the earlier review.
   The paired pilot found no Codex quality uplift and one final ZCode candidate
   timeout. Real adoption does not negate those negative results.
6. **Attribution is limited.** Native checks, model capability, human direction,
   project-specific skills and Steward coexist. Many product successes have no
   observed Steward intervention. We should credit Steward's observed role and
   the native owner separately, rather than claim every green project result.

## Public claims and next work

Claim now: **“Used across six public downstream repositories and private projects;
observed in real Codex and ZCode workflows for governance, validation routing and
documentation maintenance.”** Link this dated inventory and its public artifacts.
This is maintainer-portfolio adoption, not six independent customers.

Also claim the exact public artifact reductions and bounded failure detection
above. Keep the paired pilot as a separate usefulness experiment. Do not award a
single production score that mixes adoption, correctness, safety and efficiency.

The next work starts with existing adopters, not recruiting hypothetical ones:

- Extract three already-occurring maintenance episodes into the existing evidence
  records: what failed, what Steward routed/changed, native result, unresolved
  blocker and durable artifact. Use public commit links or anonymized summaries.
- Refresh only status rows used for a current claim. Preserve last-run revision,
  date and failure; automate projection from an existing receipt only if repeated
  manual drift justifies it. Do not add another telemetry service.
- For the next comparable episodes, record setup + maintenance + execution +
  repair burden. Retrospective logs establish use and outcomes; prospective
  paired or carefully matched comparisons test incremental benefit.
- Test the observed failure boundaries first: piped exit status, skipped evals,
  stale installations and stale evidence. External suites come after these local
  questions, with a named claim and bounded cost.

## Reproducibility and privacy

Public Git artifacts: externally auditable, with a concrete replay for size
measurements. Historical local sessions: inspected directly, not publicly
replayable. Private Git/session observations: anonymized case evidence only.
No fresh product benchmark or broad test suite was run during this audit; it
would change the question from retrospective use to present-day acceptance.
The audit does not mutate consumer repositories or publish their transcripts.
